# Универсальный поиск — backend

Независимый Python API и JSON CLI, Python 3.10+, стандартная библиотека.
Нужен SQLite с FTS5 и R*Tree (наличие проверяется при открытии индекса).
Ни интерфейса, ни изменений бизнес-логики компонентов. Сеть и LLM не нужны.

## Запуск без веб-интерфейса

Из корня репозитория сначала `cd city-sim`, затем:

```sh
export PYTHONPATH=shared
python3 -m unittest discover -s shared/universal_search/tests -v
python3 -m universal_search --db /tmp/search-demo.sqlite index-json \
  --source synthetic/example shared/universal_search/examples/synthetic.json
python3 -m universal_search --db /tmp/search-demo.sqlite search '20'
python3 -m universal_search --db /tmp/search-demo.sqlite search 'автобус 20' --type bus
python3 -m universal_search --db /tmp/search-demo.sqlite search 'Королёва 20'
python3 -m universal_search --db /tmp/search-demo.sqlite search 'Кроолева 20'
python3 -m universal_search --db /tmp/search-demo.sqlite update-state \
  --source synthetic/example shared/universal_search/examples/synthetic.json
python3 -m universal_search --db /tmp/search-demo.sqlite search 'автобус №20' \
  --bbox 158.64 53.05 158.66 53.07
```

**Все объекты и координаты этого примера синтетические**, `origin=synthetic`.
Свежесть состояния определяется его временем наблюдения; дата примера не заменяется
на текущую. CLI при ошибке адаптера возвращает exit code 1 и JSON с типом ошибки.

## Программный API

```python
from universal_search import Entity, DynamicState, SearchIndex

with SearchIndex('/tmp/my-search.sqlite') as index:
    # Только полный снимок одного авторизованного источника/области видимости.
    index.replace_source('synthetic/example', [
        Entity('bus20', 'bus', 'Автобус 20', 'synthetic/example', origin='synthetic'),
        Entity('addr20', 'address', 'Королёва 20', 'synthetic/example', origin='synthetic'),
    ])
    index.update_dynamic('synthetic/example', [
        DynamicState('bus20', 'bus', (158.65, 53.06), 'учебный пример',
                     '2026-11-23T10:00:00Z'),
    ])
    result = index.search('автобус 20', types=['bus'], limit=10)
```

`search(query, types=None, sources=None, bbox=None, limit=20,
max_age_seconds=300, now=None)` возвращает JSON-совместимый словарь:

- `intent`: `text`, `ambiguous_number` или предполагаемый тип;
- `hits`: `id`, `type`, `name`, `coordinates` (`[lon, lat]` или `null`), `source`,
  `relevance`, `origin`, `aliases`, `updated_at`, `status`, `freshness`;
- `total`: число совпадений после фильтров до `limit`;
- `warnings`, `sources`: ошибки отдельно по статическому и динамическому слою,
  время последних проверок. Ошибка источника не скрывается пустой выдачей.

Типы: `street`, `address`, `road_section`, `bus`, `equipment`, `camera`, `task`,
`event`, `base`, `snow_site`. Идентичность: **(source, type, id)**. Сохраняются
исходные ID; один ID у разных типов/источников — разные сущности. Разные источники
не склеиваются по похожим названиям или близким координатам. Для подтверждённых
межисточниковых соответствий в будущем нужен отдельный реестр связей.

`freshness.static` и `freshness.dynamic`: `fresh`, `stale`, `unknown`, `future`.
Неизвестная дата источника остаётся неизвестной, даже если индекс создан сейчас.
`indexed_at` — только время индексации; `source_available` — результат последней
попытки синхронизации, а не обещание доступности в эту секунду. Все даты входа
должны иметь часовой пояс. Порог свежести передаёт вызывающая система.

`bbox=(west,south,east,north)` фильтрует по последним известным координатам;
неизвестные координаты исключаются. Пересечение антимеридиана надо разделить на
два запроса. R*Tree даёт кандидатов, затем проверяются точные координаты.
Это поиск точек, не пересечений полилиний и не маршрутизация.

## Обновление и отказ источников

- `replace_source(source, entities)`: атомарный **полный** снимок; удаляет исчезнувшие
  сущности только данного источника. Идентичный повтор не переписывает индекс.
  Повтор одинаковой сущности в снимке допустим; конфликтующие дубликаты отвергают
  весь снимок. Не передавайте сюда одну страницу большого реестра.
- `update_dynamic(source, states)`: пакет частичных обновлений состояний. Не меняет
  FTS/словарь/`indexed_at`; обновляет только состояние и координаты в R*Tree.
  `coordinates=None` явно означает отсутствие текущей координаты, без отката к
  старой статической точке. Неизвестный ID откатывает весь пакет. Более старое
  наблюдение не перезаписывает новое; отсутствующая дата не перезаписывает известную.
  Одинаковое время принимается в порядке поступления. Пропущенный ID сохраняет
  предыдущее состояние, которое со временем становится stale.
- `sync(adapter)` / `sync(adapter, dynamic=True)`: IO выполняет адаптер; при ошибке
  остаётся последний полный индекс/состояние и появляется warning. Сырое сообщение
  исключения не публикуется, чтобы случайно не раскрыть ключи/URL.
- Планировщик обновлений остаётся у владельца источника. Статические снимки запускать
  по revision/hash/событию изменения; телеметрию — отдельным периодическим batch.
  Ядро не запускает фоновые циклы или внешние платные запросы.

Один `SearchIndex` на поток; несколько процессов/соединений работают через SQLite
WAL и timeout 5 s. Поиск выполняется в одной read-транзакции. Формат БД v1;
индекс — восстановимая проекция. При несовместимой версии создать новый файл
и загрузить источники, а не менять компонентные БД.

## Адаптеры и интеграция

Контракт `Adapter` в `adapters.py`: `source`, `entities()` и при наличии
телеметрии `states()`. Адаптер с одной статикой не обязан реализовывать `states()`;
вызывать dynamic sync для него не следует. Внешние HTTP/DB-клиенты, ограниченные
таймауты, авторизация и преобразование datetime/UUID в строки принадлежат вызывающему
коду. Поиск не отправляет запросы источникам и не зависит от их бизнес-модулей.

| Адаптер | Проверенный вход | Особенности |
| --- | --- | --- |
| `JsonAdapter` | `{entities: [поля Entity], states: [поля DynamicState]}` | Любой из десяти типов; поле `source` каждой Entity должно совпадать с адаптером |
| `OsmExportAdapter` | winter-dispatch `data/petropavlovsk.json` | ID `way/<OSM ID>`; улицы группируются по точному названию в пределах одного города; адрес только при явных `addr:*` |
| `CameraCatalogAdapter` | cam `cameras/sources.json` + `monitoring/cameras.json` | Название + координаты по ID, без URL потоков; неполная геопривязка остаётся `null` |
| `MonitoringAdapter` | JSON `/api/v1/dashboard` | Изолировать `source` по run_id, например `monitoring/demo`; статический текст и текущие статусы отдельно |
| `WinterShiftAdapter` | workspace v2 snapshot или ответ `ShiftRepository.read` | source оканчивается `/shift_id`; задания/техника/события; origin задаётся явно |

Примеры реальных входов после отдельного checkout исходных веток:

```sh
python3 -m universal_search --db /tmp/search-real.sqlite index-osm \
  /path/to/winter-dispatch/data/petropavlovsk.json
python3 -m universal_search --db /tmp/search-real.sqlite index-cameras \
  /path/to/kamchatka-cam/cameras/sources.json \
  /path/to/kamchatka-cam/monitoring/cameras.json
python3 -m universal_search --db /tmp/search-real.sqlite search 'Кроолева'
```

OSM coordinates — существующий узел way, **представительная точка**, не центр улицы
или адрес дома. OSM-имена улиц в разных городах нельзя складывать в один source.
Location notes камер сохраняют оговорки о приблизительной геопривязке.
Их координаты нельзя считать подтверждённой точкой крепления.

Dashboard ограничен 100 событиями: адаптер представляет только это окно, не весь
архив. Для полного поиска событий подключить отдельный разрешённый полный export
или отдельную проекцию событий через канонический адаптер. Исчезновение из окна
снимка удаляет запись из этой проекции. Исторические события требуют отдельного
source. Нельзя молча обозначать dashboard полной базой.

Снимок смены содержит IDs машин, а не реальную GPS-телеметрию. Начальная точка
планировщика не выдаётся за текущую позицию. События смены без исходного ID имеют
индекс в append-only списке, scoped по shift_id; перестроенный журнал считается
новым снимком. Не интерпретируются минуты симуляции как фактическое время.

Внешний HTTP API можно обернуть вокруг `search()` в существующем backend, сохранив
его авторизацию. Не надо открывать общий индекс live/demo/разных организаций
публично. `sources` — фильтр поиска, **не механизм разграничения доступа**:
вызывающая система выбирает разрешённый отдельный индекс/полный scope источников.

## Выбор архитектуры, ранжирование, ограничения

Оценка до реализации и аудит исходных веток: [DESIGN.md](DESIGN.md).

Нормализация: Unicode NFKC, casefold, е/ё, пунктуация, №, сокращения улиц,
домов/корпусов и академика. Оригинальное название хранится без изменений.
Текстовые кандидаты: FTS5 exact/prefix + словарь токенов и обратные postings.
Частичные совпадения: prefix от 2 символов, substring от 3. Опечатки: OSA distance
с перестановкой соседних букв, до 1 операции от 4 символов и до 2 от 8.
В отличие от морфологического анализатора это не гарантирует все русские падежи.

Все содержательные токены должны совпасть. Числовые/смешанные идентификаторы
с цифрами совпадают только целиком: `20` не заменяется на `21`, `200`, `20/1`.
Длинный запрос ограничен 256 символами и 12 содержательными токенами; limit 1–100.
Синтаксис FTS пользователь не задаёт: выражение строится из нормализованных токенов.

Вес совпадения: exact 1, prefix .85, substring .7, typo .65/.5. Средний вес × .8,
плюс .15 за предполагаемый тип и .05 за точное совпадение всего индексированного
текста. Равенство разрешается по source/type/id. Это **эвристическая релевантность,
не вероятность правильного ответа**. Тип из текста — мягкий приоритет; жёсткий
фильтр только через `types`. `20` сохраняет неоднозначность; `автобус 20` поднимает
автобус; `Королёва 20` поднимает адрес, при обязательном совпадении обоих токенов.
Запросы только из служебных слов (`улица`, `автобус`) возвращают пустую выдачу.

Словарь для substring просматривается целиком, для typo — по диапазону длины
через SQL индекс. Postings не требуют сканировать все сущности; скрытого лимита
кандидатов перед пространственными/типовыми фильтрами нет. Это разумный минимум
для проверенной выборки города; SLA для миллионов записей не заявляется.
При росте сначала измерить latency/объём словаря, затем заменить расширение токенов
на trigram/deletion index или backend на PostgreSQL/OpenSearch за тем же контрактом.
