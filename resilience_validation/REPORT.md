# Повышение отказоустойчивости KamDispatch

24 ноября 2026 года, Камчатка. Рабочая ветка начата от `main@9a1519d`. Изменения сформированы поверх кода продукта. Замеры до исправлений взяты из [PR #24](https://github.com/Eazyan/KamDispatch/pull/24).

## После исправлений

| Сценарий | До | После |
| --- | --- | --- |
| OpenWeather недоступен | Публичная панель возвращала старый прогноз без статуса | Последний успешный набор остаётся; backend сообщает по каждой точке время, TTL, статус и причину. Проверены 503, ответ неверной схемы, полностью просроченный ответ и fallback на трёхчасовой горизонт. |
| Остановка worker | Readiness и панель продолжали отвечать 200 без признака остановки | `/api/v1/status` сообщает `worker: stale`, останется доступен вместе с независимыми маршрутами. Readiness базы по-прежнему имеет собственную семантику. |
| PostgreSQL недоступна | Данные панели возвращали 500 | Route возвращает 503 с типом отказа и ссылкой на статус. Шлюз и City Sim продолжают отвечать; проверен повторный запуск процесса API во время отключённой базы. |
| Часть пробок устарела | У выдачи был общий срок 10 минут | Каждый интервал получает свой TTL 60 минут и статус `stale` при истечении. Старые и свежие наблюдения уживаются в одной публикации. В пробелах не появляются расчётные признаки `free`. |
| Клиент РНИС отдаёт неподвижный старый timestamp | Устаревание следовало из окна свежести выдачи | API статусов явно сообщает `positions_expired`. Просроченная позиция отсутствует в выдаче карт. |
| Полная потеря узла | В PR #24 восстановление использовало готовые образы | Сборка из Git с `--no-cache --pull` проверена до загрузки системных пакетов. Полное восстановление в этом прогоне заблокировано ответами 503 от Debian. |

Контракт для frontend описывает все пять состояний, источники, периоды и поля для серых дорожных интервалов. Файлы интерфейса и дизайн в PR не менялись. Привязка статусов к текущим визуальным элементам — отдельный frontend-шаг в будущем. [Контракт](../docs/SYSTEM_STATUS_API.md)

## Измерения

### Чтение панели и статусов

Среда — Docker Desktop на ARM64, 10 vCPU и 7,75 ГиБ RAM у VM. База содержала 1 000 синтетических обращений. На каждой ступени 12 с новых запросов, затем завершение оставшихся. Три четверти виртуальных клиентов читали dashboard, остальные — API состояния. Ответы быстрых маршрутов занимают большую долю пропускной способности. Авторами теста выбраны p95 dashboard ≤ 1 с и ошибок ≤ 1% только как диагностическая граница этого прогона.

| Клиенты | p50 / p95 / p99 dashboard, мс | Ответов/с по смеси | Ошибки / запросы | Пик CPU / RAM по сэмплам |
| ---: | --- | ---: | ---: | --- |
| 10 | 666 / 988 / 1 019 | 46,84 | 0 / 590 | 151,3% / 936 МиБ |
| 50 | 3 185 / 3 428 / 3 439 | 41,73 | 0 / 540 | 146,0% / 1 010 МиБ |
| 100 | 6 415 / 7 259 / 7 343 | 25,60 | 0 / 368 | 160,9% / 1 057 МиБ |
| 500 | 10 943 / 11 003 / 11 007 | 68,38 | 720 / 1 500 | 192,1% / 1 141 МиБ |

10 клиентов выполнили выбранный критерий с небольшим запасом. На 50 нарушена граница задержки, на 500 из 750 запросов dashboard 720 завершились клиентским таймаутом. Все 750 запросов к статусу получили 200. Пропускная способность в таблице включает завершившиеся ошибкой запросы. Пик CPU суммируется по контейнерам, 100% соответствует одному ядру. Числа RAM и CPU — максимумы по выборочным замерам. После пика часть серверных запросов продолжала выполняться. [Графики](evidence/load.png) · [Сырые метрики](evidence/experiments.json)

### Обращения, задания и снег

- 1 000 текстовых обращений от разных тестовых клиентов за 59,981 с, 16,67/с. HTTP 201 для всех, p50/p95/p99 — 21,87/45,56/119,42 мс. SQL подтвердил 1 000 записей без потерь и дубликатов. Сто повторов вернули те же идентификаторы. Повторы посланы одним залпом и измерены отдельно.
- После разрыва локального канала повтор назначения с устаревшей версией вернул 409. Принятие задания и повтор подтверждения вернули одинаковый результат. История содержит одно назначение и одно принятие.
- Из 1, 5 и 10 одновременно поданных небольших расчётов приняли и завершили 1, 3 и 3. Остальные получили ожидаемый 429. p95 подачи составил 143, 28 и 51 мс. Некорректный запрос получил 422. При остановке выполнения City API клиент достиг таймаута в 2 с. Основная страница и API состояния ответили 200. Для City API заданы 2 vCPU и 2 ГиБ, выборочный максимум во время серии составил 100,42% одного ядра и 784,6 МиБ.

### Источники и каскад

Публичный фильтр вернул прежний прогноз и отдельную причину сбоя через 1,18–1,38 с после принудительного опроса. Истёкший прогноз оставил шесть точек и получил `stale` через 76,33 с при тестовом TTL 75 с. Валидный ответ после fallback 403 дал трёхчасовой горизонт.

На одном коридоре API вернул три устаревших интервала и один свежий. Несогласованный граф не заменил последнюю совместимую публикацию, а причина появилась в `source.reason`. После возврата источника статус восстановился за 5,26 с. Замороженная отметка времени РНИС распознана за 91,35 с, просроченная позиция исчезла с карты; первая свежая позиция вернулась за 30,17 с.

При 100 параллельных клиентах с отключёнными внешними фикстурами и PostgreSQL все 3 678 запросов состояния вернули 200, p95 159 мс. City Sim health вернул 200 на 11 558 чтений. Обе версии панели вернули структурированный 503, всего 2 199 ответов при отказавшей БД, код `database_unavailable`. При одновременной остановке City API снимок состояния по-прежнему отдавался с HTTP 200. Повторный запуск API при выключенной базе подтвердил независимость маршрута.

В измеренном каскаде worker обнаружен через 33,95 с от команды остановки при пороге 40 с, PostgreSQL через 4,69 с после остановки, City API через 2,49 с. Время доступности снимка после перезапуска API — 1,87 с от начала проверок. PostgreSQL снова отмечена healthy через 6,00 с после запуска, City API через 4,62 с от начала соответствующей проверки. Worker ответил healthy на первой проверке после старта.

Штатный pytest прошёл 80 тестов, включая чтение статуса из реального PostgreSQL, холодный старт API при недоступной базе и границу TTL интервалов. [Журнал pytest](evidence/regression.log)

**Чистое восстановление — BLOCKED.** PostgreSQL, том City Sim и кадры выгружены. Сборка City API завершилась, а сборка KamDispatch остановилась на скачивании пакетов Debian с HTTP 503. Восстановление данных в новом стеке в этом прогоне не выполнялось. [Результат](evidence/recovery.json)

## Границы покрытия

- Проверены локальная сборка Linux-контейнеров, порт loopback, схемы имитации поставщиков. Настройки рабочего сервера и реальные задания в тест не входили.
- Аудит камер F02 в этой итерации не повторялся. Проверки синтетической базы и JPEG использовали уже существующие демонстрационные кадры.
- Порог для замеров чтения введён только как диагностический критерий. Результаты относятся к конкретной смеси, железу и окну. Краткий прогон не оценивает реальный спрос и длительное накопление ресурсов.
- Доставка через Telegram/MAX и локализация адресов на реальной карте не испытывались. Повтор назначения проверял версию и историю через API. Сообщения наружу не отправлялись.
- Зависание имитировалось приостановкой City API и наблюдением клиентского таймаута. Бесконечный цикл отдельно взятой задачи и принудительная отмена вычислительного потока не испытывались. Очередь ограничена тремя активными задачами.
- РНИС со старым временем измерения эмулирован. Координаты, которые остаются прежними при корректно меняющемся timestamp, могут означать штатную остановку. Реальный поток не использовался.
- Чистая сборка запускалась без кэша приложения. Docker Hub, GitHub, npm и PyPI оставались доступны на этапе сборки. Полная потеря площадки и внешних реестров одновременно вне покрытия.
