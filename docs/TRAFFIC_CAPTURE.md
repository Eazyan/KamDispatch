# Учебный перенос пробок 2ГИС на OSM

Дата проверки: 23 ноября 2026, Asia/Kamchatka. Основа: KamDispatch `123927c`.
Текущее сопоставление: `source_lines_geometry_match_v3`, отдельная модель: `osm_adjacency_smoothing_v1`; ранняя версия v1 сохранена в истории ниже.

Это ручной эксперимент: обычный Chrome открывает публичную карту Петропавловска,
сохраняет одинаковый вид без пробок и с пробками, после чего Python сопоставляет
изменившиеся цветные линии с существующими OSM-отрезками. Результат — GeoJSON и
страница Leaflet с подложкой OpenStreetMap. API мониторинга, база, очередь заданий,
автобусные наблюдения и City Sim не меняются. Фонового сбора нет.

## Запуск

Нужны Python 3.12+, обычный Google Chrome/Chromium и графическая сессия. На Linux
можно запускать команду через `xvfb-run -a`. Ключи API, `.env` и пользовательский
профиль браузера не требуются. Интернет нужен для 2ГИС, Leaflet CDN и плиток OSM.

```bash
python3 -m venv .venv-traffic
.venv-traffic/bin/pip install -r requirements-traffic.txt
.venv-traffic/bin/python scripts/capture_traffic.py capture out/traffic-pilot
# Linux: добавить --chrome /usr/bin/google-chrome
# Другой участок: --center 158.653 53.0358 --zoom 16
python3 -m http.server 8095 --bind 127.0.0.1 --directory out/traffic-pilot
# Открыть http://127.0.0.1:8095/review.html
```

Каталог для `capture` должен быть новым: прежние измерения не перезаписываются.
Команда завершается с ненулевым кодом при блокировке, ошибке UI или неверной
геопривязке. CAPTCHA не обходится; повторные автоматические попытки не запускаются.
Не закрывайте и не перемещайте карту вручную во время сбора.

Повторный offline-анализ сохранённой пары, без Chrome и запросов к 2ГИС:

```bash
.venv-traffic/bin/python scripts/capture_traffic.py analyze out/traffic-pilot
```

`--roads` принимает JSON или gzip с существующим контрактом
`{"segments":[{"id":"...","name":"...","coordinates":[[lon,lat],...]}]}`.
По умолчанию используется `monitoring/snow_roads.json.gz`; сборщик не восстанавливает
дорожную сеть из изображения и не запрашивает новый OSM-снимок.

## Что сохраняется

- `traffic-off.png`, `traffic-on.png`: исходные снимки полного окна 1440×1000 CSS px.
- `capture.json`: источник, центр, масштаб, четыре UI-точки, область анализа,
  времена получения и SHA256 обоих изображений. Время обновления данных провайдером
  неизвестно (`provider_updated_at=null`).
- `traffic-lines.geojson`: отдельные выделенные фрагменты 2ГИС, полученные до чтения OSM.
  Линии доступны также в `roads.geojson.traffic_lines` и отдельным слоем страницы проверки.
- `matched-sections.geojson`: локальные сопоставленные фрагменты OSM длиной от 6 CSS px;
  доступны также в `roads.geojson.matched_sections`. Неизвестные промежутки не соединяются.
- `roads.geojson`: исходные OSM-ID/геометрия и `traffic_status`: `free`, `slow`,
  `congested`, `unknown`. Это классы отображения, не измеренные скорости.
- `model-estimates.geojson`: отдельные модельные классы и веса, источники, расстояние
  по графу и причина отказа от оценки; доступны также в `roads.geojson.model_estimates`.
- `review.html`: статичная страница проверки на OSM. Она не обновляется сама.
- `capture-failure.json`: причина неудачи, если сбор не закончен.

Артефакты предназначены для локальной проверки, сохраняйте их под `out/` (gitignored).
Исходные изображения 2ГИС не включаются в PR. Перед регулярным сбором или публикацией
производного слоя следует проверить условия использования данных провайдера.

## Как проверяется привязка и распознавание

1. Карта открывается с севером наверху, без наклона, при zoom 16–18. Через меню
   «Что здесь?» читаются координаты четырёх заранее выбранных точек экрана.
   Внутренние API/токены 2ГИС не используются.
2. Первые три точки задают аффинное преобразование WebMercator → пиксели. Четвёртая
   проверяется независимо: ошибка более 1 px, поворот или вырожденные точки
   прерывают анализ. Такой контроль проверяет геопривязку, не качество трафика.
3. В центральном прямоугольнике `[460,220,880,460]` сравниваются пиксели пары снимков.
   Сохраняются изменившиеся цвета; неизменный зелёный фон не является трафиком.
4. **До доступа к OSM** OpenCV выделяет связные цветовые компоненты и векторизует
   их `HoughLinesP`. Тонкие линии сохраняются; небольшие компактные значки отбрасываются.
   Кандидаты проверяются по непрерывности цветового сигнала вдоль собственной геометрии.
   Получается отдельный набор линий с цветовым классом и координатами, независимый от OSM.
5. Точки выделенных линий сопоставляются с ближайшими OSM-полилиниями: расстояние
   не более 12 CSS px, разница продольной ориентации не более 20°. Близкие конкурирующие
   параллельные дороги остаются неразрешёнными. Поперечный переулок не получает цвет
   только за близость к перекрёстку. Это геометрическая ориентация, не направление потока.
6. Продольная проекция ограничена концами OSM-сегмента с допуском дискретизации 2 px:
   линия за концом дороги не должна наблюдать её конец. Локальные непрерывные совпадения
   одного класса длиной от 6 px сохраняются отдельно, включая неполностью наблюдаемые
   дороги. В viewer этот слой включён по умолчанию; оценка всей дороги — отдельный слой.
   По сопоставленным линиям агрегируется покрытие OSM-отрезка. Требуются 60% полной
   длины и доминирование класса 75%; абсолютного барьера 40 px больше нет. Исходные
   линии и их ID доступны для проверки назначения. Неизвестная часть дороги не считается
   свободной. Граница области включается с шагом 2 px, поэтому число видимых отрезков
   может немного отличаться от v1 с шагом 4 px и внутренним отступом.
7. Хеши исходных снимков проверяются перед анализом; в результат записывается хеш
   дорожного снимка. Изображения сохраняются в CSS scale, чтобы Retina DPR не менял
   систему координат. При ошибке четвёртой точки или размеров анализ останавливается.

запустить `scripts/evaluate_traffic.py --capture pilot-2=DIR2 --capture pilot-4=DIR4
--baseline pilot-2=V2_DIR2/roads.geojson --baseline pilot-4=V2_DIR4/roads.geojson
--output out/traffic-evaluation-v3.json`. Для исходного инструментального разбора
v2 сохранены локальный `audit_traffic_matching.py` и полный JSON в каталоге сессии

категорий зафиксированы в JSON аудита. Локальные файлы могут исчезнуть после очистки tmp.

Проверки: регрессии частичного покрытия, разрыва, ROI, конкурирующих параллельных
дорог и концов в обоих направлениях. Мутации удаления endpoint-проверки и удаления
локальных секций возвращают соответствующие AssertionError. Полная регрессия и
браузерная проверка перечислены в PR. Пользователь видит локальный красный сигнал
на Ленинградской, даже когда вся улица не получает один класс; это основание для
ручной проверки задержки техники, а не автоматического назначения маршрута.

Следующий учебный шаг: размечать пропуски и ложные назначения именно на дорогах,
сохранять OSM `highway/service/oneway` при импорте и сравнить геометрические кандидаты
с учётом связности графа. Не назначать цвета неназванным дорогам по одному имени и
не снижать порог whole-road ради количества окрашенных участков.

## Модельные оценки: 23 ноября 2026, Asia/Kamchatka

Решение пользователя: для цели минимум 170 из исходных 184 допустимы наблюдения
и **отдельно обозначенные модельные оценки**. Источники остаются прежними:
публичная UI-пара 2ГИС от 22 ноября и дорожный OSM-снимок из репозитория.
Новые API, платные данные, библиотеки и фоновые процессы не добавлялись.
База перед изменением: `aed25c0`; текущий код и SHA данных закреплены в
[модельном отчёте](traffic-model-evaluation-2026-11-23.json).

Инвентарь минимального изменения: существующий `match_traffic_lines` оставлен
для наблюдений; `monitoring/traffic_image.py` дополнен `estimate_traffic`.
В доступных `monitoring/` и `scripts/` готовой реализации графового переноса нет.
Существующие capture/analyze, evaluator и viewer расширены; отдельный сервис,
БД, универсальный ML-слой или маршрутизатор не строятся. Это оценка класса
коридора, а не расчёт маршрута, скорости, направления или времени прибытия.

Рассмотрены: продолжить только прямое сопоставление (не даёт информации при
отсутствии лент); переносить ближайший цвет по прямой (может перескочить через
несвязанные дороги); переносить по OSM-связям. Выбран последний вариант.

1. Наблюдаемые классы целых дорог и нормированные по длине локальные секции
   становятся источниками. Исходные наблюдения не изменяются.
2. Дороги соседствуют **только при общей исходной координате OSM**. Пересечение
   линий на экране без общего узла не соединяет их. По графу дорог считается
   приближённое расстояние между центрами: вес связи — половина суммы длин дорог.
   Это не граф движения с поворотами/односторонностью; расстояние не является
   точной длиной автомобильного маршрута.
3. Для неизвестной дороги берутся три ближайших наблюдаемых OSM-way в пределах
   1000 м. Дубликаты сегментов одного way не умножают его голос. Вес источника:
   `4 × exp(-distance/250) × observed_coverage`. К этим голосам добавлен один
   голос сглаженного приора выборки (Laplace +1 на каждый из трёх классов).
4. Источники частичных секций могут распространять свой класс на остальную
   дорогу **только как модель**. Наблюдаемое поле `traffic_status` остаётся unknown.
   Базовый приор без доступного графового источника не даёт итоговый класс.
5. Если доля вклада соседних наблюдений в суммарном весе меньше 10%, модель также
   воздерживается. Это технический порог, выбранный после изучения снимка,
   **не откалиброванная вероятность точности**. Нормированные `class_scores` —
   относительные веса классов. Выборка видимых магистралей смещена и не описывает
   частоты состояний всех дворов/улиц; приор нельзя считать дорожным наблюдением.

Начальная модель с восемью соседями дала 24/27 совпадения при сокрытии OSM-way,
но пропустила все три красных участка (balanced agreement 50%). Проверены варианты
`neighbors=3/8`, `decay=100/250 м`; выбран простой вариант 3/250. Обе тройки дали
27/27 на тех же данных. Эти 27 классов использованы при выборе параметров:
**100% здесь не являются независимой валидацией**. Регрессия отдельно защищает
ситуацию, когда множество дальних зелёных дорог заглушает близкий красный сигнал.

Для оценки дополнительно скрываются целые пространственные квадранты. В каждом
прогоне удаляются и целые, и частичные источники скрытых OSM-way, включая их
сегменты в других блоках. Проверяется отсутствие утечки источников в приор.
Это согласие с ранее полученными классами снимка, а не с независимыми полевыми
данными; три красных участка относятся к одной локальной ситуации, не к трём
независимым заторам.

| Проверка pilot-4, 27 известных классов | Модель | Приор «всегда свободно» |
| --- | ---: | ---: |
| Сокрытие одного OSM-way, данные подбора параметров | 27/27 | 24/27 |
| Сокрытие квадранта, общее согласие | 23/27 (85,19%) | 24/27 (88,89%) |
| Сокрытие квадранта, средняя полнота двух классов | 91,67% | 50% |
| Восстановлены красные / ложные красные на свободных | 3/3 и 4/24 | 0/3 и 0/24 |

Модель повышает чувствительность к локальной задержке, ценой ложных предупреждений;
она не улучшила обычную accuracy относительно приора в блочной проверке.
На полностью зелёном pilot-2: сокрытие way 22/22, сокрытие квадранта 21/22,
один отказ от оценки; заторы на этом снимке проверить невозможно.

**Итог на фиксированных исходных 184 ID: 27 наблюдаемых целиком + 143 модельных
= 170 оценённых (92,39%), 14 без оценки.** Среди 143 модельных: 124 по соседям,
19 с использованием собственной частичной секции. В 14 отказах: 8 без графового
источника в радиусе, 6 со вкладом наблюдений менее 10%. Считались только конечные
классы free/slow/congested с графовой опорой, приор и локальная секция сами по себе
не засчитывались как оценка всей дороги. При более слабом критерии получилось бы
176; эти шесть дополнительных классов намеренно не принимаются.

184 ID и SHA исходного v1-выхода закреплены в `tests/fixtures/traffic_annotations.json`
(`pilot-4.target_road_ids`). Новые граничные четыре дороги не подменяют знаменатель.
В `capture.json` копии можно указать `target_road_ids`: analyze проверит наличие всех
целей в области снимка и выведет только их, используя полный граф для модели.
Сырые исходные capture/PNG не изменяются: создайте новый каталог копий.

```python
# After copying the three capture input files into out/traffic-model:
import json
from pathlib import Path
path = Path('out/traffic-model/capture.json')
capture = json.loads(path.read_text())
references = json.loads(Path('tests/fixtures/traffic_annotations.json').read_text())
capture['target_road_ids'] = next(c['target_road_ids'] for c in references['captures'] if c['id'] == 'pilot-4')
path.write_text(json.dumps(capture, indent=2))
```

```bash
python scripts/capture_traffic.py analyze out/traffic-model
python scripts/evaluate_traffic.py --capture pilot-4=out/traffic-model \
  --minimum-assessed 170 --output out/traffic-model-evaluation.json
```

`--minimum-assessed` проверяет фиксированные target ID, отсутствие пропавших целей
и число принятых оценок; недостаток завершает команду с ошибкой. В отчёте сохранены
ID наблюдений/модельных оценок/отказов, причины, параметры и SHA. Исходные PNG
по-прежнему нужны для повторного расчёта и не включаются в PR.

В viewer наблюдения показаны сплошной линией, модель — пунктиром в отдельном слое,
включённом по умолчанию. В карточке модели указаны источник, расстояние, вклад
наблюдений, веса классов и дата исходного снимка. Модель рисуется под наблюдаемыми
секциями. Изображение 22 ноября не представляется текущим движением 23 ноября.

Проверки включают несвязанные пересечения, ограничение расстояния, отказ без
наблюдений и при слабом вкладе, отсутствие изменения наблюдаемого результата,
независимость приора от сегментации, сокрытие целого way и частичных источников,
фиксированный знаменатель. Мутации расширения соседей до восьми и отключения
порога возвратили соответствующие AssertionError. Независимое ревью, браузерная
и полная регрессии фиксируются в PR после выполнения.

Практическое решение диспетчера: пунктирный красный участок — повод запросить
проверку или уточнить резерв времени техники. Он не является подтверждённой
пробкой и не должен автоматически запрещать выезд. Для студентов 2–4 курса
следующий шаг — независимая разметка нескольких дат/районов, данные OSM о типах
дорог и направлениях, проверка ложных красных и настройка порога на отдельной
выборке. Для этого достаточно сохранённых демоснимков, OSM и бесплатного Python.

## Границы результата

- `direction=unresolved`, `evidence_scope=road_corridor`: направление движения
  не восстанавливается. Нельзя назначать одну оценку двум направлениям как факт.
- `coverage_fraction` — доля длины с распознанным цветом, не вероятность верности.
- У дорог 2ГИС и OSM бывают разные оси, развязки и сегментация. На соседнюю дорогу
  может попасть чужая линия; пиксельный буфер это полностью не исключает.
- Текст, значки, реклама, изменение стиля/камеры и антиалиасинг остаются источниками
  ошибок. Четыре точки не доказывают полноту загрузки слоя и отсутствие всех
  перекрывающих элементов. Перед использованием нужна визуальная сверка пары.
- Оценки помечены `experimental_unvalidated`; скорости и время поездки не выдаются,
  `not_for_automatic_dispatch=true`. Данные не направляются в очередь диспетчера.
- Нулевой контрольный остаток не подтверждает фактическую дорожную ситуацию.

## История версии v1

Следующие результаты относятся к прежнему поиску пикселей около оси OSM; это не описание текущего алгоритма.

### Проверки и решения

Использован подход из LAB: отдельный временный профиль обычного Chrome и Playwright
через локальный CDP. Код LAB, его БД, карточки студий и настройки не импортируются.
Рассмотренные кандидаты: существующие `monitoring/bus.py` (работает с GPS и временем,
не с изображениями) и `scripts/build_overview_map.py` (рендерит OSM, не извлекает
трафик). Поэтому добавлены чистый анализатор `monitoring/traffic_image.py` и одна
ручная команда; новый сервер, публичный API и миграции не нужны.

Независимый тест сначала падал на отсутствии дорожных features, затем прошёл.
Мутация с отключением сравнения подложки снова вызвала ожидаемое падение:
`unchanged green basemap ... cannot prove free flow`. После возврата кода тест зелёный.
Остальные проверки включают ошибку четвёртой точки, смешанные цвета, короткий значок,
тонкий текст, несовпадающие размеры, частичное покрытие и подмену файла снимка.

На первом реальном локальном прогоне визуальная сверка выявила два ложных жёлтых
участка рядом с подписью храма. Добавлены проверки толщины и минимальной протяжённости;
после повторного анализа снимка: 112 участков, 7 `free`, 105 `unknown`, ошибка
четвёртой точки <0,01 px. Это подтверждает выполнение цепочки и осторожное
распознавание, но не полевую точность. Сырые снимки остаются локально.

Дальнейшая проверка для студентов: вручную разметить 10–20 участков на нескольких
сохранённых снимках, посчитать ошибки отдельно от доли неизвестных и сравнить
с независимыми автобусными проездами. До этого оценки не использовать как точные
веса маршрутизатора. Произвольные коэффициенты скорости по цвету не вводить.

Источники: [управление слоем 2ГИС](https://docs.2gis.com/en/mapgl/map/configuration/controls),
[публичная карта](https://2gis.ru/p_kamchatskiy),
[© OpenStreetMap contributors](https://www.openstreetmap.org/copyright).

Повтор на втором виде (`158.653, 53.0358`, zoom 16): 184 участка, 11 `free`,
1 `congested`, 172 `unknown`; контрольная ошибка <0,01 px. Красный участок вручную
сопоставлен с видимой красной линией 2ГИС. Одна предыдущая попытка на этом виде
остановилась по таймауту контекстного меню; GeoJSON при отказе не создан. Повтор
выполнен вручную. Устойчивость UI при длительном сборе не подтверждена.

Независимое ревью выявило расхождение CSS/device pixels при Retina DPR=2. Добавлены
`scale="css"` для обоих снимков и проверка размеров по `capture.viewport` до анализа.
Регрессия сначала падала `DID NOT RAISE`, после исправления проходит. На настоящем
Chromium DPR=2 обычный снимок 400×320, CSS-снимок 200×160 при viewport 200×160.

Offline-группа имеет отдельный workflow `traffic-capture.yml`, который устанавливает
`requirements-traffic.txt` и запускает 12 проверок без сети 2ГИС и без браузера.
В обычном окружении без NumPy эта опциональная группа пропускается; приложение
мониторинга не получает новую обязательную зависимость. Интеграционные тесты
PostgreSQL запускайте на новой временной базе: существующие тесты оставляют данные,
повтор на той же базе может падать на старых строках и уникальности `bus_hints`.


## Переработка v2 и проверка полноты

22.11.2026, Asia/Kamchatka: по замечанию пользователя перестроен порядок обработки.
Сначала выделяются линии 2ГИС, затем выполняется геометрическое сопоставление с OSM.
Существующие `color_mask`, калибровка и CLI использованы повторно. Удалены эрозия тонких
линий и абсолютный минимум 40 px. Вместо собственной реализации векторизации применяется
OpenCV. Новый offline-скрипт оценки добавлен, поскольку прежний CLI только создаёт данные
и не сравнивает их с ручной разметкой. Сервисные API и БД не менялись.

Ручная разметка: `tests/fixtures/traffic_annotations.json`, 23 положительные полилинии
и 12 отрицательных контролей на двух сохранённых снимках. Сначала выбраны видимые
ленты на исходных изображениях, приблизительные опорные точки привязаны к ближайшим
пикселям нужного цвета в пределах 20 px, затем разметка визуально проверена. Порядок
и ограничения записаны в JSON; полная перепись всех линий города не выполнена.
Второй снимок выделен как holdout; параметры выбирались по первому.

Оценка измеряет длину ручной разметки, не число случайно окрашенных дорог:
- извлечение: эталонная линия нужного класса находится в пределах 5 px от выделенной;
- перенос: эталонная линия находится в пределах 12 px от окрашенной OSM-линии того же
  класса, продольные направления отличаются не более чем на 20°;
- отрицательные контроли: доля нетрафикового отрезка, ошибочно покрытая выделением;
  случай считается ложным при покрытии от 20%. Это не глобальная precision.

| Сохранённый вид | Линий в разметке | Полнота выделения v2 | Перенос на OSM v1 → v2 | Ложные контроли v2 |
| --- | ---: | ---: | ---: | ---: |
| pilot-2, разработка | 9 | 81,24% | 24,43% → 81,45% | 1 из 6 |
| pilot-4, holdout | 14 | 93,12% | 81,23% → 81,23% | 0 из 6 |

Покрытие ручной разметки на holdout при переносе не выросло: прежняя версия уже
окрашивала размеченные магистральные фрагменты. На общем наборе прежних 184 OSM-ID
число участков с оценкой выросло с 12 до 27, но это отдельный показатель покрытия,
не доказательство правильности новых назначений. В полном v2-экспорте 188 участков
(24 free, 3 congested, 161 unknown); четыре добавились из-за нового шага у границы.

Остаточная ошибка: два зелёных фрагмента логотипа на pilot-2 попали в выделение;
на OSM они не назначились. Надёжность на произвольных стилях, масштабах, погоде
и плотных развязках не установлена. Полевая скорость и направление по-прежнему
не определяются; автоматическая диспетчеризация не подключена.

Воспроизведение требует тех же исходных снимков: их SHA256 зафиксированы в разметке,
изображения в репозиторий не включены. Передайте пути к сохранённым capture-каталогам:

```bash
.venv-traffic/bin/python scripts/evaluate_traffic.py \
  --capture pilot-2=/path/to/pilot-2 \
  --baseline pilot-2=/path/to/v1-pilot-2/roads.geojson \
  --capture pilot-4=/path/to/pilot-4 \
  --baseline pilot-4=/path/to/v1-pilot-4/roads.geojson \
  --output out/traffic-evaluation.json
```

Полный отчёт с покадровыми значениями, SHA256 разметки, кода, дорожного графа
и изображений: [traffic-evaluation-2026-11-22.json](traffic-evaluation-2026-11-22.json).
Новые offline-тесты проверяют короткую смещённую линию, поперечный переулок,
конкурирующие параллельные дороги, компактный значок и независимость выделения от OSM.
